## 3. Compliance jurídico — análise crítica (camada que pode FECHAR o produto)

### 3.1 OAB — Provimento 205/2021 (publicidade) e 94/2000 atualizados

**Risco real:** A Dra. Jacira é advogada inscrita. Tudo que sair do produto fala em nome dela ou pode ser interpretado como tal. O Provimento 205/2021 + Código de Ética OAB veda:

- **Captação de clientela** (art. 5º Provimento 205) — formas vedadas: contato direto não solicitado, mensageria a pessoas que não pediram, anúncios sensacionalistas. Onde Jurify falha: WhatsApp inbound é OK (cliente iniciou), mas **bulk template send / campanha** (mencionado em "próximas ondas pendentes" da memória) seria captação ativa proibida sem consentimento prévio inequívoco.
- **Garantia de resultado** — `src/lib/multiagents/agents/CommercialAgent.ts:24` declara "NUNCA garante resultado" no prompt; e `agent-prompts.ts:195` reforça "NUNCA prometa resultado". Bom. **Mas nenhum guardrail técnico** impede o LLM de prometer; é só prompt. Risco residual: alucinação do gpt-4o-mini gerando "vamos ganhar essa ação fácil".
- **Honorários públicos** — `CommercialAgent.ts:28-38` lista tabela de honorários por área. **Provimento 205 art. 7º veda divulgação pública de honorários** salvo em contrato individual. Se essa tabela vazar (UI ao cliente final, link público) = infração disciplinar.
- **Identificação como IA** — Decreto regulamentando LGPD + diretrizes ANPD/AI-Act recomendam transparência sobre interlocutor. Hoje a Dra. Jacira (agente IA) responde como se fosse a advogada real. **Sem disclaimer "sou um assistente IA do escritório, vou conectar você com a advogada"**. Risco: cliente final pode alegar engano (CDC art. 6º), MP-Defesa do Consumidor. Já tem disclaimer no prompt do `juridico` ("você é um assistente de informação jurídica, NÃO um advogado licenciado") mas o `juridico_bancario` (Dra. Jacira) NÃO tem disclaimer claro de IA — se passa por humana.

**Mitigação P0:**
- Inserir frase de abertura mandatória no agente Jacira: "Oi! Sou a assistente virtual da Dra. Jacira. Vou ajudar a entender seu caso e marcar uma conversa com ela."
- Migrar tabela de honorários do prompt (texto) para um lookup por `tenant_id` em DB, marcar privado, NÃO incluir no contexto de mensagens cliente-facing por padrão.
- Adicionar feature flag `tenants.consent_outbound_messaging` default false. Bulk send só roda com flag ON + opt-in registrado por número.

## 4. Segurança — gaps e atacantes

### 4.1 Token Supabase commitado em repo

**Verificação:** Pesquisei por `eyJhbGciOiJIUzI1NiI` (header padrão JWT) em `e:\Jurify\supabase\` — não encontrei. Memória menciona "JWT hardcoded removido (migration 20260410000001)". **Status: parece OK no código atual, mas histórico git provavelmente ainda contém** (memória já apontou: "BFG Repo Cleaner não confirmado"). Atacante que clona o repo e roda `git log -p --all | grep eyJ` pode achar credenciais antigas.

**Mitigação:** Rotacionar TODAS as keys Supabase (JWT_SECRET, anon, service_role) — se ainda não foi feito desde 04-10 quando hardcoded foi removido — e executar `git filter-branch`/BFG. Antes do go-live público.

### 4.2 OAuth state CSRF — Google Calendar

`supabase/functions/google-calendar/index.ts:267-275` — state recebido do client é apenas validado por comprimento mínimo (>=16 chars). Se cliente não envia, server **gera state e ignora**. **Não há binding entre state e session** — não armazena em `oauth_states` table com user_id. Atacante CSRF clássico: induz vítima logada a abrir URL OAuth com state controlado pelo atacante → callback associa Calendar do atacante ao Jurify da vítima.

**Mitigação P1:** criar tabela `oauth_pending_states(state, user_id, created_at, expires_at)`. `initiateAuth` insere; `exchangeCode` valida contra `req.user.id`. Já existe encrypt/decrypt — basta uma migration.

### 4.3 HMAC Webhook validation — WhatsApp/Kapso

`whatsapp-webhook/index.ts:25` — comentário diz "global fallback removido 2026-04-10 P0-3". Bom: agora é per-tenant via `getWebhookSecretByPhoneId`. Verificar se tenants reais têm `kapso_webhook_secret` populado em `configuracoes_integracoes` — se não, webhook **rejeita** mensagem (boa default). Mas operacional: novo onboarding precisa registrar esse secret. Verificar wizard.

### 4.4 RLS forced

Memória 04-23 dizia "RLS forced 1/76". Isto significa **75 tabelas têm RLS habilitado mas NÃO forced**, ou seja, role `postgres` (e qualquer SECURITY DEFINER mal escrito) bypassa. Em multi-tenant é risco crítico. Migrations recentes (`20260507000003_conversation_state_stateful_pipeline.sql`) usam `SECURITY DEFINER SET search_path` (boa prática), mas o universo de funções precisa auditoria.

### 4.5 Rate limiter em memória (já apontado)

`_shared/rate-limiter.ts` — fallback in-memory inútil em edge function stateless. Se DB-based rate limit cair (Supabase outage), **abre flood** de OpenAI calls → custo + DDoS-amplificação.

### 4.6 CORS

Já tightened (`_shared/cors.ts`) — regex `/^https:\/\/jurify-[a-z0-9]+-alef-vieiras-projects\.vercel\.app$/`. Bom. Único deploy preview do projeto match. **OK.**

### 4.7 Supabase project "Missãocumprida"

Memória 04-23 alerta projeto `Missãocumprida` (us-east-1, criado 03-13) NÃO é staging conhecido. **Risco:** dados de prod podem estar replicados/expostos lá; ou é resíduo de iteração descartada. **Investigar urgente:** quem tem acesso, há dados, deve ser deletado.

## 9. Custos OpenAI por tenant — análise rápida

Por mensagem WhatsApp inbound, hoje:
1. `analyze-whatsapp-sentiment` (gpt-4o-mini) — fire-and-forget
2. `extract-whatsapp-data` (gpt-4o-mini function-calling) — fire-and-forget
3. `agent-orchestrator` (gpt-4o-mini) — decide agente
4. agente especialista (gpt-4o-mini) — gera resposta
5. opcionalmente `summarize-whatsapp-conversation` (gpt-4o-mini) — cache invalidado por msg_count
6. opcionalmente `suggest-whatsapp-reply` × 3 (gpt-4o-mini) — sugestões de resposta

Estimativa: **5-8 chamadas por mensagem inbound**. Se conversa típica = 10 mensagens cliente, **50-80 chamadas / lead qualificado**. A R$0,0008/1k input + R$0,003/1k output (gpt-4o-mini), avg 2k tokens/call = **~R$0,80 / lead**. 1000 leads/mês = R$800. Aceitável SE plano Pro = R$199/mês captura 5+ leads convertidos.

**Risco:** loop infinito ou tenant abusivo (bot enviando spam) → 10000 mensagens/dia → R$240/dia / R$7200/mês de OpenAI sob a mesma `OPENAI_API_KEY`. `_shared/ai-budget.ts` existe e enforça `budget_limit` por tenant em `ai_usage` — **verificar se está populado**: se `budget_limit IS NULL` ou 0 = sem ceiling.

**Mitigação P1:** migration default `budget_limit_day = 50000 tokens` (≈ R$0,20/dia) + `budget_limit_month = 500000` para todos os tenants trialing. Plan upgrade libera mais.
