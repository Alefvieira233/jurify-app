# Story 2.1: Criptografia de Credenciais Phase 2 e CHECK Constraints

## Status: Draft
## Sprint: 2
## Estimativa: 12 horas
## Prioridade: P1

## Descricao

Completar a cadeia de criptografia de credenciais: cifrar OAuth tokens do Google Calendar e API keys de integracoes externas (Kapso, etc.) usando as Edge Functions `encrypt-data`/`decrypt-data` deployadas no Sprint 1. Adicionar CHECK constraints em colunas de status para garantir integridade de dados no banco, e indexes complementares em crm_followups. Apos esta story, zero credenciais estarao em texto plano no banco de dados.

## Notas Tecnicas

### Criptografia via Edge Functions
```typescript
// Criptografar
const { data } = await supabase.functions.invoke('encrypt-data', {
  body: { data: plaintext_token }
});

// Descriptografar
const { data } = await supabase.functions.invoke('decrypt-data', {
  body: { data: encrypted_token }
});
```

### CHECK Constraint Example
```sql
ALTER TABLE leads
ADD CONSTRAINT chk_leads_status CHECK (
  status IN ('novo_lead', 'em_contato', 'qualificado', 'proposta', 'negociacao', 'convertido', 'perdido', 'arquivado')
);
```

### Rollback
- DEB-004/DEB-044: Leitura dual permite rollback transparente. Se decrypt falhar, fallback para plaintext.
- DEB-010: `ALTER TABLE {table} DROP CONSTRAINT chk_{table}_status` se valores invalidos detectados.

### Risco de Regressao
- **MEDIO** para criptografia: Testar todos os fluxos que usam tokens/keys antes de remover colunas plaintext.
- **MEDIO** para CHECK: Valores de status nao mapeados serao rejeitados. Auditar DISTINCT antes de criar.
