# Story 1.1: Corrigir Isolamento Multi-Tenant e API Keys

## Status: Draft
## Sprint: 1
## Estimativa: 10 horas
## Prioridade: P0

## Descricao

Corrigir as duas vulnerabilidades criticas de seguranca que permitem vazamento de dados entre clientes: tenant_id nullable em 10 tabelas (dados orfaos escapam do RLS) e API keys armazenadas em texto plano sem scoping por tenant. Em um sistema juridico com dados protegidos por sigilo profissional (Art. 34 OAB) e LGPD, estas falhas representam risco real e imediato de vazamento de dados entre escritorios.

## Notas Tecnicas

### Estrategia de Backfill (DEB-001)
```sql
-- Exemplo para whatsapp_messages
UPDATE whatsapp_messages wm
SET tenant_id = wc.tenant_id
FROM whatsapp_conversations wc
WHERE wm.conversation_id = wc.id
AND wm.tenant_id IS NULL;

-- Rows sem relacao -> tabela orfaos
INSERT INTO _orphaned_whatsapp_messages
SELECT * FROM whatsapp_messages WHERE tenant_id IS NULL;
DELETE FROM whatsapp_messages WHERE tenant_id IS NULL;

-- Constraint
ALTER TABLE whatsapp_messages ALTER COLUMN tenant_id SET NOT NULL;
```

### Schema API Keys (DEB-002)
```sql
ALTER TABLE api_keys
ADD COLUMN key_hash TEXT,
ADD COLUMN salt TEXT,
ADD COLUMN key_prefix TEXT,
ADD COLUMN tenant_id UUID NOT NULL REFERENCES tenants(id);

-- Funcao de validacao
CREATE OR REPLACE FUNCTION validar_api_key_v2(p_key TEXT, p_tenant_id UUID)
RETURNS BOOLEAN AS $$
  SELECT EXISTS (
    SELECT 1 FROM api_keys
    WHERE tenant_id = p_tenant_id
    AND key_hash = encode(digest(p_key || salt, 'sha256'), 'hex')
  );
$$ LANGUAGE sql SECURITY DEFINER;
```
